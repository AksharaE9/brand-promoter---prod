## 1. Non-Minified Reproduction & Crash Point

### The Exact Crash Site
- **File:** `frontend/src/components/Candidate/MatchScoreChip.jsx`

- **Field Name:** `topMissing` (derived from `primaryScore.missingMustHaves`) and `topStrengths` (derived from `primaryScore.matchedRequirements`).
- **Call Stack:**
  ```

      → ul (Line 221)

          → div (Line 185)
  ```

### Why It Crashed
In candidate `cmte8fv0d00biktn7fsl4f1f4`, `primaryScore.missingMustHaves` contains:
```json
[
  { "skill": "Communication", "category": "leadership_signals" },
  { "skill": "Customer handling", "category": "sales_bd" },
  { "skill": "Lead generation & follow-up", "category": "sales_bd" },
  { "skill": "Interest in sales / marketing", "category": "career_interest" }
]
```
The backend `attachMatchScoreToCandidate()` in `backend/src/modules/candidates/routes.js:234` passed:
`topMissing: Array.isArray(primaryScore.missingMustHaves) ? primaryScore.missingMustHaves.slice(0, 2) : []`
This sliced the raw objects `[{ skill: 'Communication', category: '...' }]` without extracting a plain string label.
In `MatchScoreChip.jsx`, the tooltip renders:
```jsx
{topMissing.map((m, idx) => (
  <li key={idx} className="flex items-start gap-1">
    <span className="text-rose-400 font-bold leading-none">•</span>
    <span className="truncate">{m}</span>
  </li>
))}
```
When `{m}` is an object, React 18/19 throws **Minified React Error #31 ("Objects are not valid as a React child")**.

### Code Path Provenance
- All 297 rows in the production database were generated by `backend/src/modules/matching/scorer.js` with `scorerVersion: 1.0.0` and `parserVersion: 1.0.0`.
- Lines 150-165 of `scorer.js` push objects:
  ```js
  matchedRequirements.push({ skill: skillName, category, evidence, strength });
  missingMustHaves.push({ skill: skillName, category });
  ```
- **The Divergence:** `ResumeAnalysisTab.jsx` expected objects with `{ m.skill, m.category }`, whereas `MatchScoreChip.jsx` expected plain strings `{m}`. Because the backend serialized `matchedRequirements` and `missingMustHaves` directly into `topStrengths` and `topMissing` on `matchSummary`, the object shape caused `MatchScoreChip` to crash whenever `topMissing` or `topStrengths` was populated.

## 4. Client Error Reporting: Root Cause of `POST /api/client-errors → 404`

1. **Relative Fetch URL in Error Boundaries:**
   - Both `frontend/src/components/CardErrorBoundary.jsx:23` and `frontend/src/components/ErrorBoundary.jsx:21` execute:
     ```js
     fetch('/api/client-errors', { method: 'POST', ... })
     ```
   - In production, the browser context origin is `https://brand-promoter-prod.vercel.app`.
   - The browser sends the request to `https://brand-promoter-prod.vercel.app/api/client-errors`.
   - Vercel hosts the static React bundle with no serverless handler for `/api/client-errors`, returning **`404 Not Found`**.
2. **Missing Backend Handler:**
   - The Render backend (`brandpromoter-backend.onrender.com`) had **zero routes** defined for `/api/client-errors`. Even if the URL had resolved to the backend, it would have returned `404 Not Found`.

## 5. Error Boundary Layout Audit

1. **Candidate Profile Page (`CandidateProfile.jsx`):**
   - Has **NO section-level error boundaries**.
   - Line 653 mounts `<MatchScoreChip>` directly in the header.
   - When `MatchScoreChip` threw React Error #31, the error bubbled all the way to the top-level `ErrorBoundary.jsx`, replacing the **entire profile screen** with the generic "Something went wrong" crash screen.
2. **All Candidates List View (`Candidates.jsx`):**
   - Individual cards are wrapped by `<CardErrorBoundary>`.
   - When `MatchScoreChip` threw on a card, `CardErrorBoundary` caught it, replacing that card with "Unable to display this candidate · Retry".
   - Because the underlying data shape was still an object, clicking "Retry" re-rendered the same card, crashing again immediately.
   - A chip failure should **never take down an entire card**.

## 6. Intermittent Chunk-Loading Trigger Audit (The 10 Known Causes)

1. **Cause 1 (Ref Not Ready when Observer Configured) — APPLIES (Major):**
   - In `PaginatedListView.jsx:37`, `useEffect` runs with dependencies `[hasNextPage, isFetchingNextPage, fetchNextPage]`.
   - On initial mount while `isLoading && items.length === 0`, skeleton cards are rendered and the sentinel `div` (`ref={sentinelRef}`) is **not in the DOM**.
   - `sentinelRef.current` is `null`, so the effect returns early.
   - When the first chunk arrives, `items` becomes 48, but `hasNextPage` remains `true`. Because `hasNextPage`, `isFetchingNextPage`, and `fetchNextPage` have not changed, the effect **does not re-run**, leaving `sentinelRef.current` unobserved until the next page reload.
2. **Cause 2 (Stale Callback Closure) — APPLIES:**
   - The observer callback in `PaginatedListView.jsx:46` captured the initial closure of `fetchNextPage` and `isFetchingNextPage`.
3. **Cause 3 (Sentinel Visible from the Start) — APPLIES:**
   - On wide desktop screens (1920px+ with 4 columns), 48 cards occupy only ~12 rows (~1000px). The sentinel is already within `rootMargin: '800px'`. If no scroll occurs, no intersection state change event is fired.
4. **Cause 4 (Scroll Root Element Timing) — APPLIES:**
   - `document.querySelector('.os-content')` was evaluated once synchronously during effect setup. During initial page navigation (`PageMotion`), `.os-content` may not be mounted or measured yet.
5. **Cause 5 (Page Transition Animation) — APPLIES:**
   - `PageMotion` wraps pages with framer-motion opacity / transform transitions. If layout settles after observer attachment, intersection geometry is miscalculated.
6. **Causes 6-10 (Virtualizer, Cache, StrictMode) — APPLIES (Secondary):**
   - Lack of a visible "Load more" button left users stranded with no fallback mechanism.

## 7. Next Steps: Corrective Architecture Plan
1. **Data Contract:** Create `MatchItem` canonical schema: `{ label: string, category?: string, evidence?: string, strength?: string }`.
2. **Database Repair:** Script with `--dry-run` to convert all 297 `missingMustHaves` and `matchedRequirements` records to `{ label, category, evidence, strength }`.
3. **Backend Output Hardening:** Guarantee list endpoints output `topStrengths: string[]` and `topMissing: string[]` as flat strings.
4. **Frontend Defense in Depth:** Implement `renderItemText(item)` in `MatchScoreChip` and `ResumeAnalysisTab`.
5. **Scoped Chip Error Boundary:** Wrap `MatchScoreChip` in `<ChipErrorBoundary>` so chip failures never hide cards.
6. **Section Boundaries on Profile:** Add `<SectionErrorBoundary>` around Header, Resume Analysis, Interviews, and Offers.
7. **Backend `POST /api/client-errors`:** Add rate-limited error collection route and wire `buildApiUrl('/client-errors')` in the frontend.
8. **Deterministic Sentinel Trigger:** Callback ref for sentinel, latest-value refs, and "Load more" fallback button.
